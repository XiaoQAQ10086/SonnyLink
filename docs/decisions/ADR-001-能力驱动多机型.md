# ADR-001：能力驱动（Capability-Driven），不做机型驱动

- **状态**：已采纳
- **日期**：2026-09-30
- **依据**：ILCE-6300 (a6300) 实机实测（批次 2 / 3 / 4）

---

## 1. 背景：为什么必须这样设计

### 实测事实 A —— 同一台机器，能力集随状态变化

| 状态 | getAvailableApiList 方法数 |
|---|---|
| 连接后（未进遥控模式） | **7** |
| startRecMode 后 | **13 → 23** |
| startLiveview 后 | **23**（新增 actTakePicture、awaitTakePicture） |

**同一台 a6300，同一套固件，能力集在 7 / 13 / 23 之间浮动。**

### 实测事实 B —— 「固件支持」≠「此刻能用」

getMethodTypes 返回约 **67 个真实方法**，包含
setIsoSpeedRate / setShutterSpeed / setFNumber / setWhiteBalance / setFocusMode / startMovieRec / setTouchAFPosition …

但在 Smart Remote Control 模式下，getAvailableApiList **只暴露 23 个**，上述 setter 调用会返回
{"error":[1,"Not Available Now"]}。

### 结论

> **如果连同一台机器在不同时刻的能力都不一样，按机型写死功能就必然是错的。**

跨机型（a6000 / a5100 / a7 / RX100M3 / QX100 / AS 系 …）只会差异更大。

---

## 2. 决策

1. **客户端代码中不存在任何 model == "ILCE-6300" 之类的分支。**
2. 所有功能开关由运行时 getAvailableApiList 决定。
3. **每次状态切换后重新查询**并重建能力集（startRecMode / startLiveview / 拍照后 / 重连后）。
4. 任何调用失败（[1,"Not Available Now"] / 403 / 超时 / 连接断开）一律视为「该能力此刻不可用」，静默降级 + 记日志，**不弹错误对话框**。
5. **端口 / 端点 / DD 文件名一律从 SSDP 的 LOCATION + DD.xml 读取**，不硬编码。
   实测证据：a6300 的 DD 在 **61000**，控制在 **8080** —— 而公开案例里是 64321 / 8080 / 10000 / 60152。
6. liveview 分辨率**不预置**，直接读实际 JPEG 尺寸。

---

## 3. 机型档案（camera-profiles/）的定位

> **只用于三件事：测试基准、已知怪癖记录、回归验证清单。**
> **不参与运行时分支。**

新机型的接入成本 = 跑一次 probe（约 3 分钟）→ 生成 camera-profiles/&lt;MODEL&gt;.md → 如有怪癖则补一条记录。**不需要改代码。**

---

## 4. 能力 → UI 映射（核心设计）

**UI 默认隐藏所有控件**，收到能力集后才显示 —— 保证在任何机型上都不会出现「点了报错」的按钮。

| 能力（出现在 availableApiList） | UI 表现 |
|---|---|
| startLiveview | 显示取景区 |
| actTakePicture | 显示快门按钮 |
| awaitTakePicture | 快门后轮询结果 |
| getAvailableExposureCompensation + setExposureCompensation | 曝光补偿滑杆（范围来自 getAvailable） |
| actZoom | 变焦按钮 |
| getSupportedSelfTimer + setSelfTimer | 定时自拍选择 |
| getAvailableShootMode + setShootMode | 拍摄模式切换 |
| setIsoSpeedRate / setShutterSpeed / setFNumber 等 | **仅在出现时才显示**（a6300 的遥控模式下不会出现） |
| 一个都没有 | 只显示取景 + 快门 |

在 a6300 上，实际会显示的控件是：
**取景区 + 快门 + 曝光补偿 + 变焦 + 定时自拍 + 拍摄模式**。
（ISO / 快门 / 光圈 / 白平衡 / 对焦 / 录像都不会显示，因为相机不在这些模式下暴露它们。）

---

## 5. 机型支持边界

| 类别 | 判定依据 | 结论 |
|---|---|---|
| 🟢 **Camera Remote API 时代机型** | 在官方兼容清单内 **且** 相机端有遥控入口 | ✅ 支持 |
| 🟡 **无遥控入口的老机型**（疑似 NEX-5R/5T/6） | 相机菜单里找不到入口 | ❌ 不支持（**相机端限制，软件无能为力**） |
| 🔴 **新世代机身**（a7 IV / a6700 / a1 / FX 系） | 索尼已移除 Camera Remote API | ❌ 不支持（需另开 PTP/CRSDK 路线） |

---

## 6. 为未来留的口子（传输层抽象）

定义传输层抽象（Kotlin）：

- discover()            —— SSDP + DD.xml 发现
- call(method, params)  —— JSON-RPC，**串行**
- openLiveview()        —— 返回帧流
- close()

本期只实现 **ScalarWebApiTransport**。
未来若要做新机型（PTP/CRSDK），**新增一个实现即可，上层 UI 与能力层不变**。

## 7. 权衡与代价

| | |
|---|---|
| **代价** | 需要一层「能力 → UI」映射，比硬编码多一点代码 |
| **收益** | 新机型零代码成本；永远不会出现灰色/报错按钮；调试时能直接看到「相机此刻能做什么」 |
| **风险** | 能力判定错误会导致 UI 缺控件 |
| **缓解** | 保守隐藏 + 内置一个「调试面板」显示原始 getAvailableApiList 和调用日志，便于用户反馈 |

---

## 8. 如何验证一个未知机型（标准流程）

1. 跑 probe 批次 3 + 4
2. 检查 getApplicationInfo 版本是否 ≥ 2.0.0（低于则直接不支持）
3. 检查 getAvailableApiList 是否含 startLiveview
4. 记录 liveview 实际分辨率 / 帧率 / 单帧大小
5. 导出能力矩阵 CSV（batch5 产出）
6. 落成 camera-profiles/&lt;MODEL&gt;.md

---

## 9. 读能力 vs 写能力（★ 核心设计修正 ★）

实测发现：**能读到的参数，远多于能设置的参数。**

- `getAvailableIsoSpeedRate` / `getAvailableFNumber` / `getAvailableShutterSpeed` … 全部返回 `ERR 1 Not Available Now`
- 但 `getEvent` 的返回里**照样有** fNumber 5.0（候选 3.5–22）、isoSpeedRate AUTO、focusMode AF-S、exposureMode Manual、shutterSpeed 候选列表

**→ 因此能力模型必须是两个维度：**

| 维度 | 数据来源 | 用途 |
|---|---|---|
| **读能力** | `getEvent` 的字段 | **显示**（状态栏：光圈 / 快门 / ISO / 对焦模式 / 曝光模式） |
| **写能力** | `set*` 出现在 `getAvailableApiList` 且调用成功 | **控件启用** |

在 a6300 上最终呈现：
- **可显示**：光圈 5.0 · 快门 · ISO AUTO · AF-S · Manual · 曝光补偿 ±15
- **可设置**：曝光补偿、拍摄模式、变焦、定时自拍

## 10. 已知的性能基线（a6300）

| 指标 | 实测 |
|---|---|
| 分辨率 | **640 × 424**（唯一档位，`startLiveviewWithSize` / L / M 全部不可用） |
| 帧率 | **波动很大：4.4 – 19 fps**（同样 ~32 KB 单帧，批次 4 得 4.41，批次 5 得 14.73） |
| 有效吞吐 | 0.77 – 3.71 Mbps，**不稳定** |
| 无线链路（参照） | 802.11n / 2.4GHz 信道 1 / 协商 **65 Mbps** / RSSI -61 dBm |
| **瓶颈判定** | **不在无线链路，在相机端的取景生成** |
| postview 下载 | 1616×1080 / 407 KB / 1242 ms |
| **取景中直接拍照** | **2485 ms，且流不中断** ✅（首选方案） |
| 停流拍再开流 | 2691 ms，中间黑屏（不采用） |
| stopLiveview | 106–595 ms |
| getEvent 往返（取景中） | 384 ms |

> ⚠️ 帧率波动 3 倍以上是本机型最需要关注的特性 → **客户端必须实时显示 fps 并在 UI 上诚实反映**。
