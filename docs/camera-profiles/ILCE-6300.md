## 4. LiveView（实测，逐字节验证）

- URL：`http://192.168.122.1:8080/liveview/liveviewstream`
- HTTP 响应头：`200 OK` / `Content-Type: application/octet-stream` / **`Transfer-Encoding: chunked`**
- **每个 HTTP chunk 恰好 = 一个完整 liveview 包**
- 容器结构（81/81 包全部满足 `chunkSize == 136 + payloadSize + paddingSize`，0 例不符）：

| 偏移 | 长度 | 字段 | 实测值 |
|---|---|---|---|
| 0 | 1 | start_byte | `0xFF` |
| 1 | 1 | payload_type | `0x01`（JPEG 帧） |
| 2 | 2 | sequence_number (u16 BE) | 1,2,3,… 严格递增，无重复 |
| 4 | 4 | timestamp (u32 BE) | 单调递增，单位 ms |
| 8 | 4 | start_code | `0x24 35 68 79` = "$5hy" |
| 12 | 3 | payload_size_wo_padding (u24 BE) | 6016（首帧）/ 6272（其后） |
| 15 | 1 | padding_size | `0x00` |
| 16–135 | 120 | 保留区 | 全 0 |
| 136 | paySize | JPEG | SOI 固定落在 data[136] |

- **分辨率：640 × 424**（40 帧全部一致，无 EXIF/JFIF，SOI 后紧跟 DQT）
- **帧大小：5967 – 6222 B，p50 = 6195 B**
- **帧率**：
  - 冷启动首 ~10 帧很慢（~5.9 fps，ts 间隔 ~170 ms）
  - **稳态 ts 中位间隔 52 ms → ≈ 19.2 fps**
  - 15 秒窗口平均 **15.45 fps**（232 帧 / 15.01 s）
- **吞吐：96.8 KB/s ≈ 0.93 Mbps**
- ❌ `getAvailableLiveviewSize` → `{"id":1,"error":[1,"Not Available Now"]}`
  → **分辨率不可协商，固定 640×424**

## 6. 已知限制

1. **固件支持 ≠ 当前可用**：`getMethodTypes` 显示固件**支持** `setIsoSpeedRate` / `setShutterSpeed` / `setFNumber` / `setExposureCompensation` / `setWhiteBalance` / `actZoom` / `setTouchAFPosition` 等（共约 67 个方法），
   但在 Smart Remote Control 模式下 `getAvailableApiList` **只暴露 23 个** → 这些 setter 调用会失败。
   → **客户端必须以 getAvailableApiList 为准，不能以 getMethodTypes 为准。**
2. `postviewImageSize` 仅 `"2M"`，不可选。
3. `shootMode` 仅 `"still"`（不可录像）。
4. LiveView 分辨率固定 640×424，不可提升。
5. 同一时刻只允许**一个** liveview 客户端。
6. `stopLiveview` / `stopRecMode` 均正常返回 `{"result":[0]}`。

### 7.2 ★ 真实场景下的码率与帧率 ★

| 指标 | 全黑画面（批次3） | 真实场景（批次4） |
|---|---|---|
| 分辨率 | 640×424 | 640×424 |
| 单帧 min/p50/avg/max | 5967 / 6195 / 6195 / 6222 B | 26721 / 32405 / 31934 / 38242 B |
| 实测帧率 | 15.45 fps | **4.41 fps** |

**结论：取景链路是「约 1 Mbps 带宽受限 + 帧率自适应」，且模型吻合：**

    帧率 ≈ 1 Mbps / (8 × 单帧字节数)
    6 KB/帧  → 理论 20.8 fps，实测 15.45 fps
    32 KB/帧 → 理论  3.9 fps，实测  4.41 fps

**场景越复杂、细节越多，帧率越低。**

→ 待测：连接相机时读取 netsh wlan show interfaces 的协商收发速率（批次 5）。

## 8. 结论：客户端必须「能力驱动」，绝不能「机型驱动」

## 9. 批次 5 实测结果（2026-09-30）

### 9.1 ★ 无线链路诊断 —— 瓶颈不在无线 ★

| 项目 | 实测值 |

| 频段 / 信道 | 2.4 GHz / **信道 1** |

### 9.2 ★ 帧率是「波动的」，不是固定值 ★

| 批次 | 场景 | 单帧 p50 | 实测 fps | 有效吞吐 |
|---|---|---|---|---|
| 3 | 全黑 | 6,195 B | 15.45 | 0.77 Mbps |
| 4 | 真实场景 | 31,934 B | **4.41** | 1.15 Mbps |
| 5 | 真实场景 | 31,968 B | **14.73** | **3.71 Mbps** |

**同样的单帧大小（~32 KB），批次 4 得 4.41 fps，批次 5 得 14.73 fps —— 波动 3 倍以上。**
结论：**不存在「固定 1 Mbps 上限」**；相机端吞吐不稳定（可能与预热、AF 工作、温升、瞬时 RF 重传有关）。
→ 客户端必须**实时显示 fps** 并自适应，不能假设固定帧率。

### 9.7 ★★ 重大发现：读能力 ≠ 写能力 ★★

`getEvent` 返回里**包含完整参数状态**，即使对应的 `getAvailable*` 全部失败：

    exposureMode: "Manual"
    fNumber: "5.0"          fNumberCandidates: ["3.5" … "22"]
    isoSpeedRate: "AUTO"
    focusMode: "AF-S"
    flashMode: "on"
    exposureCompensation: min -15 / step 1 / max 15 / current 0
    selfTimer: 0, 候选 [0, 2]
    postviewImageSize 候选: ["Original", "2M"]
    zoomInformation: zoomPosition 0, zoomNumberBox 1
    shutterSpeed 候选: ["30\"", "25\"" … ]

**→ 即使不能「设置」光圈/快门/ISO，也能从 getEvent「显示」它们。**

能力模型因此必须分成两个维度：
- **读能力**（数据来自 `getEvent`）→ 状态栏**显示**
- **写能力**（`set*` 在 availableApiList 且调用成功）→ 控件**启用**

- `netsh` 输出在脚本里出现中文乱码（GBK/UTF-8 混淆）。数值可读，后续脚本需先 `chcp 65001` 或指定编码。

## 10. ★ 重要发现：payloadSize 不是 JPEG 长度 ★

（2026-09-30，写解析器时被单元测试抓出）

ILCE-6300 容器里的 payloadSize 是**相机内部缓冲区的大小**，不是 JPEG 长度。
JPEG 的 EOI 之后还跟着几十字节**上一帧残留的脏数据**（缓冲区未清零）。

| 包 | payloadSize | 真实 JPEG (SOI..EOI) | 尾部残留 |
|---|---|---|---|
| 0 | 6016 | **5967** | 49 B |
| 1 | 6272 | **6193** | 79 B |
| 2 | 6272 | **6193** | 79 B |
| 3 | 6272 | 6198 | 74 B |
| 4 | 6272 | 6206 | 66 B |
| 8 | 6272 | 6233 | 39 B |

### 判定依据

连续几帧的尾部字节是**同一条序列的滑动窗口**：

    包2 尾部 = 00 00 00 84 48 0d c7 db d1 90 ...
    包3 尾部 = 00 00       db d1 90 ...          ← 前移 4 字节
    包4 尾部 = 00 00             3c ba 70 89 ...  ← 再前移

这正是「复用未清零缓冲区」的特征。而且尾部含 FF AD 这类**非法熵编码字节**
（JPEG 熵编码里 0xFF 后只能是 0x00 或合法标记），证明它不是图像数据。

### 对客户端的硬性要求

1. **必须按 SOI..EOI 切帧**，不能拿 payloadSize 当图像长度。
2. 直接把整段 payload 丢给 JPEG 解码器通常也能出图（解码器遇 EOI 会停），
   但长度统计、内存分配、"最后一帧是否完整"的判断都会错。
3. 实现（core-liveview）：
   - LiveviewFrame.jpegBytes() 返回裁剪后的干净 JPEG
   - LiveviewFrame.jpegLength / trailingBytes 暴露诊断信息
   - payloadSize 仍保留用于容器层校验（136 + payloadSize + paddingSize == chunkSize，实测 81/81 吻合）
4. 单元测试 payloadSizeIsBufferSizeNotJpegLength 锁定该行为。

### 对既有指标的影响

- 之前报告的「单帧 p50 = 6195 B / 32405 B」是用 SOI/EOI 扫出来的 —— **是对的**
- 「吞吐 XX KB/s」是按收到的总字节算的 —— **略偏高**（含 chunk 头与残留数据），误差 < 2%

## 12. 能力边界（权威结论 · 2026-10-01 二次探测）

本节记录「这台相机通过 Smart Remote Control 到底能做什么」的最终结论。
**所有条目都有 App 内实机调用证据**（写入 `Android/data/com.sonnyapp/files/probe.txt`），不是推测。

### 12.1 通过 ✅

| 能力 | 方法 | 实测证据 |

| 实时取景 | startLiveview | 640x424，稳定 15~20 fps |
| 拍照 | actTakePicture | 往返 2.0~2.5 s，**取景流不中断** |
| **曝光补偿** | get/set/getAvailable/getSupportedExposureCompensation | 范围 **-15..+15，步进 1**；★ 仅取景运行期间可用 |

| 方法 | 取景停止时 | 取景运行时 |
|---|---|---|
| **setExposureCompensation** | ❌ 不在列表 | ✅ **在列表** |
| actZoom | ❌ | ❌（怀疑需要电动变焦 PZ 镜头） |
| awaitTakePicture | ❌ | ❌ |

⚠️ **重大教训（差点做错设计）**：

早期探测是「先把取景停掉，再逐个试方法」，结果把 `setExposureCompensation` 误判成不可用 ——
**它只在取景运行期间开放**。如果按那个结论做，P2 的曝光补偿滑杆就被砍掉了。

> **任何能力探测都必须在目标状态下进行。** 这次修正后做了「取景运行中每 10 秒采一次可用方法列表」的常驻诊断。

### 12.4 固件声明 vs 实际可用（两个不同的问题）

| 概念 | 含义 | 数量 |
|---|---|---|
| getMethodTypes | **这个固件的代码里有这个方法** | **67** |
| getAvailableApiList | **当前状态下相机允许你调用** | 7 / 12 / 14 / **21** / **22** / 24 之间浮动 |

大量方法固件里有、但**在遥控模式下永不开放**（触摸对焦、录像、画质设置都是这类）。

**结论：能力判断必须以 getAvailableApiList 为准；getMethodTypes 只能说明「这个固件可能存在该方法」。**

| 原计划 | 结论 |
|---|---|
| P2 曝光补偿滑杆 | ✅ **可行**（仅取景期间） |
| P2 变焦 | ⚠️ 能力驱动，非 PZ 镜头自动隐藏 |
| P2 定时自拍 / 拍摄模式 / 状态栏 | ✅ 可行 |
| **P4 触摸对焦** | ❌ **不支持**（固件限制，官方 App 同样如此） |

> 但**取景 + 拍照 + 曝光补偿 + 定时自拍 + 状态显示**已经能构成一个可用的遥控 App。

## 13. 官方 App 对照

对 Imaging Edge Mobile 7.8.5（com.sony.playmemories.mobile）做字符串级分析，
用于确认是否存在本机未使用的端点。

### 13.1 结论：无遗漏

| 检查项 | 结果 |
|---|---|
| 官方 App 引用的相机方法 | **65 个**，与固件声明的 67 个基本重合 |
| 本机 DD.xml 扩展标签 | 仅有 X_ScalarWebAPI_Version / ServiceList / Service / ServiceType / ActionList_URL —— **无 LiveView URL 标签** |
| App 内 HTTP 路径常量 | /accessControl /avContent /camera /contentSync /sony /system /appControl —— **本机仅 /sony** |
| temporarilyUnavailableApiList | **本机事件中不存在该字段** |
| 本机事件字段 | 17 个，含 touchAFPosition（恒为 currentSet:false），但既不在可用列表也不在临时不可用列表 |

官方 App 中出现的 PTP/IP 相关类（如 EnumLiveviewImageQuality）属于**另一套协议**
（USB 或新机型的 Wi-Fi 遥控），与 ScalarWebAPI 不通用。

### 13.2 多机型扩展点

官方 App 引用、本机固件没有的方法，即更新机型具备的能力：

| 类别 | 方法 |
|---|---|
| 画质 / 格式 | getAvailableStillQuality, setStillQuality, getSupportedStillSize, setStillSize |
| 跟踪对焦 | actTrackingFocus, getTrackingFocus, setTrackingFocus, getAvailableTrackingFocus |
| 快门半按 | actHalfPressShutter, cancelHalfPressShutter |
| 录像 | startMovieRec, startAudioRec, startIntervalStillRec, startLoopRec |
| 升降格 | startSuperSlowRecRecording, actSuperSlowRecBuffering |
| 白平衡 / AE 锁定 | actWhiteBalanceOnePushCustom, getAELock |

这些正是能力驱动架构的价值：换到支持它们的机型后，UI 会自动出现对应控件。

### 13.3 触摸对焦结论

三条独立证据一致：

1. **直接调用**：setTouchAFPosition 等 4 个方法全部返回 ERR 1（三种坐标约定均试过）
2. **可用列表**：8 次不同状态采集，从未出现任何对焦方法
3. **官方 App**：实机确认官方 App 同样无法触摸对焦，其 TouchAfController 受同一套可用性检查约束

**结论：该机型在 Smart Remote Control 模式下不支持触摸对焦。**

## 14. getAvailableApiList 不能用于判断「参数是否可写」

### 14.1 现象

| 曝光模式 | 可用方法数 | 列表含 setExposureCompensation？ | 实际可否调用？ |
|---|---|---|---|
| **Aperture（A）** | 22 | 有 | 可以 |
| **Manual（M）** | 21 | **没有** | **也可以** |

**列表里没有，不等于调用会失败。**

### 14.2 原因

getAvailableApiList 反映的是固件对「当前状态下是否把该功能暴露给第三方」的判断，
可能因曝光模式、对焦模式、菜单设置等原因，隐藏一个实际可用的方法。

JSON-RPC 端点本身并不校验该列表，直接调用仍会成功并返回 result[0]。

### 14.3 由此确定的两条规则

1. **写操作**：不查列表，直接调用，以相机回应为准（callAndCheck）
2. **UI 显隐**：用语义信号判断，不使用方法名列表
   - 曝光滑杆：检查 getEvent 是否报告有效的 EV 范围（min < max）
   - 仅在写入真正失败时提示用户
